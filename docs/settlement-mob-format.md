# Подключаемые MOB поселений: контракт этапов 2–6

Этап 6: физический каталог карт x64 — **`Maps64`**. MPR, MOB, MQ, GRP,
вторичные MOB и фоновые карты читаются из него; старый `Maps` запасным источником
не является. Готовый [кандидат Посёлка и его состав](settlement-content.md)
содержит отдельный `Maps64/settlements/1m_poselok.mob` и реестр revision 3.
Он подготовлен для ревью, без установки и игровой проверки.

Реализация находится в `task/X64PEACE01`. Она добавляет загрузчик и пространство
имён к существующему миру EIRebuild64. Этап 3 добавляет мирную область и локальные
ворота. [Кандидат Посёлка](../data/settlements/zone1-poselok.candidate.json) хранится
в исходниках; в установленном моде он не активирован. Игровые MOB и население
не меняются.

Этап 4 добавляет [диалоги в существующем мире с полной паузой](settlement-dialogues.md).
Темы и награды используют этот реестр и полные имена; NPC и сами ключи
доступности пока не перенесены. Namespace-завершение требует токена активной
сессии разговора, а не отдельного клиентского сообщения о завершении.

## Регистрация

Реестр читается из `settlements.json` в корне загруженного мода. Отсутствие файла
означает пустой реестр. Это описание ресурсов, без отдельного переключателя
в конфигурации. Номер поселения постоянен и не зависит от порядка записей.

Пример ниже показывает будущую регистрацию; его нельзя применять к исходному
`basecam.mob` целиком. Файл `settlements/poselok.mob` ещё предстоит подготовить.

```json
{
  "version": 1,
  "settlements": [
    {
      "id": 1,
      "revision": 1,
      "map": "zone1",
      "mob": "settlements/poselok.mob",
      "dependencies": [],
      "aliases": { "Elder": 1000054752 },
      "object_imports": { "Hero": "Hero", "VGate": 1725 },
      "group_imports": { "Heroes": "Heroes" },
      "state_imports": {
        "q.": "q.",
        "z.": "z.",
        "FirstComing": "FirstComing",
        "techTime": "techTime"
      },
      "briefings": {
        "s1": { "text": "s1", "reward": "s1" },
        "constr_1": { "shop": 1 }
      }
    }
  ]
}
```

| Поле записи | Смысл |
|---|---|
| `id` | Обязательный положительный номер до `INT_MAX`. Для Посёлка — 1, префикс `1m_`. |
| `revision` | Обязательная положительная редакция содержимого. При изменении MOB или привязок автор увеличивает её. |
| `map` | Обычная карта, с расширением `.mpr` или без него. Сравнение путей без учёта регистра; начальное `Maps64/` (или прежнее логическое `Maps/`) убирается. |
| `mob` | Отдельный MOB относительно каталога Maps64 мода. Абсолютные пути и компоненты `.`/`..` запрещены. Необязателен для регистрации только мирной области; зависимости без главного MOB запрещены. |
| `dependencies` | Дополнительные MOB этого же поселения в явном порядке; загружаются перед главным MOB модуля. Весь набор использует одно пространство имён. |
| `aliases` | Дополнительные смысловые имена существующих локальных ID. Имена из поля объекта MOB также становятся псевдонимами, кроме пустого имени и `none`. |
| `object_imports` | Местное имя → числовой ID основной карты, имя её персонажа или полная ссылка другого поселения на той же карте. |
| `group_imports` | Местное имя группы → уже объявленная глобальная группа. `Heroes:group` разделяет существующую группу и её индекс; новая пустая группа не создаётся. |
| `state_imports` | Общие GS-ключи. Точное имя либо отображение префикса, оканчивающегося точкой с обеих сторон. Выбирается самое длинное совпадение; регистр сохраняется. |
| `briefings` | Местная тема → явные имена текста, записи награды QDB и/или номер существующего магазина. Требуется `text` или `shop`; `reward` необязателен. |
| `peace` | Необязательные граница мирной области, ворота, фракция и параметры тревоги; см. ниже. Требуется хотя бы одно из `mob` и `peace`. |

Привязка `shop` открывает [торговлю в живом мире](settlement-trade.md) поверх
диалога с той же полной паузой. `text` у неё задаёт подпись; вступительная речь
и награда оформляются отдельной темой. Торговля не завершает брифинг и не меняет
доступный GS-ключ темы на 2.

Неизвестные поля, повторные JSON-ключи, номера поселений и файлы одного набора,
конфликтующие псевдонимы, отсутствующий локальный ID, циклические объектные импорты
и дублирование локальных ID между зависимостями отклоняются. Один набор содержит
не более 256 MOB, реестр — 4096 поселений. Зависимости здесь являются явным
списком файлов, а не графом с неявным рекурсивным поиском.
Имена вида `id67` зарезервированы для прямой ссылки на локальный ID и не могут
служить произвольным объектным импортом или псевдонимом другого объекта.

## Имена и ссылки

| Исходное обращение внутри модуля 1 | Разрешённая сущность |
|---|---|
| `GetObject(67)` или `GetObjectByID("67")` | Локальный объект `1m_id67`. Для больших ID следует использовать строковую форму, чтобы не терять точность `float`. |
| `GetObjectByID("1m_id67")` | Именно объект 67 поселения 1; допустимо и из основного сценария. |
| `GetObjectByName("Elder")` | Местный псевдоним `1m_Elder`. |
| `GetObjectByName("Hero")` при показанном импорте | Герой основной карты. |
| `GetObjectByName("VGate")` при показанном импорте | Существующие ворота Zone1, ID 1725. |
| `GlobalVars(Elder:object)` | Переменная `1m_Elder`; объектное значение задаётся сценарием. |
| `GlobalVars(Hero:object)` при импорте | Переменная `1m_Hero`, привязанная к герою; привязка обновляется при входе в контекст потока после появления отряда. |
| `Script VCheck#0#1(...)` и его местный вызов | Сценарий `1m_VCheck#0#1`. |
| Вызов `2m_VCheck#0#1(...)` | Явный вызов уже объявленного сценария поселения 2. |
| `GSSetVar(0,"Village",1)` | GS-ключ `1m_Village`. |
| `GSSetVar(0,"b.Elder.s1",1)` | GS-ключ `b.1m_Elder.1m_s1`. |
| `GSGetVar(0,"q.quest")` при импорте `q.` | Общий ключ `q.quest`. Без импорта обращение отклоняется. |

Неполное местное имя из модуля не ищется среди одноимённых переменных или
сценариев основного MOB. Полная неизвестная ссылка даёт ошибку; она не проходит
через `atoi` и не превращается в хеш одноимённого персонажа основной карты.
Обычные сценарии без контекста поселения сохраняют прежнее разрешение имён.
Объявить переменную или сценарий с чужим префиксом нельзя; явный вызов уже
объявленного сценария другого модуля сохраняет контекст его владельца.

Префикс применяется при компиляции объявлений, глобальных переменных и вызовов.
GS-ключи разрешаются при исполнении, включая вычисленные строки и команды
`GSGetPlayerVar`/`GSSetPlayerVar`. Произвольные строковые аргументы, пути ресурсов,
локализованный текст и имена предметов автоматически не переименовываются.
Имена переменных и GS-ключей сохраняют исходный регистр; объектные псевдонимы
сопоставляются без учёта регистра.

`GetObjectStringID` возвращает для объекта модуля полную строку `1m_id67`, которую
можно безопасно передать в `GetObjectByID`. Внутренние числовые ID выделяются из
свободных диапазонов движка с сохранением признака сюжетного персонажа. Они
являются деталями исполнения, а не постоянными публичными ID. Числовая привязка
резервируется за модулем до выгрузки мира, включая удалённые объекты.

Объектные импорты не создают копий героя, ворот или персонажей другого модуля.
Они могут временно разрешаться в отсутствующий объект, например до размещения
героя. Локальный неизвестный ID и неизвестный псевдоним являются ошибками.
Числовые ID импортов учитываются при распределении внутренних ID, в том числе
для ещё не размещённых героев и наёмников.

## Загрузка и исполнение

Загрузчик вызывается после основного MOB и до завершения загрузки зоны. Он
сначала разбирает все подходящие модули и составляет таблицы ID, затем создаёт
объекты, после этого компилирует сценарии в соответствующем контексте. Файлы
зависимостей компилируются в порядке регистрации. Для обращения к более позднему
сценарию требуется обычный `DeclareScript`.

Заголовок дополнительного MOB не меняет время, ветер, дипломатию или граф
навигации основной карты. Объектные AI-логики читаются штатным читателем.
`p_nParentTemplate` относится к шаблону базы, а не к объекту карты, и не
перенумеровывается. Координаты объектов и сценарных команд используются как
записаны: пересчёт размещения из basecam в готовый Посёлок относится к переносу.

Ошибка чтения, создания или компиляции прерывает загрузку зоны. Уже созданные
объекты модуля удаляются, сценарии очищаются, карта помечается незагруженной.
Частично работающего поселения загрузчик не оставляет.

`WorldScript` нового модуля ставится в очередь штатным механизмом. Владелец
записан у каждого потока: условия, действия, вложенные циклы и продолжение после
ожидания исполняются в одном контексте. Пространство имён не определяется
порядковым `!N!` вторичного MOB.
Загрузка модуля и его событий не меняет счётчик прежних вторичных MOB.

`AddMob` из контекста поселения допускает только уже загруженный файл его
объявленного набора и не загружает его повторно. Необъявленная зависимость —
ошибка. Загрузка файла действующего модуля через обычный `AddSecondaryMob` без
контекста запрещена. Исходные динамические AddMob basecam потребуется отдельно
адаптировать при переносе; этот этап не исполняет их в обход регистрации.

При повторной свежей загрузке той же карты с поселением перечитывается весь
набор, чтобы прежние статические объекты не переживали новый экземпляр модуля.
Возврат в сохранённую зону должен идти через штатное восстановление состояния.
Повторный прямой вызов загрузчика для уже загруженных модулей отклоняется до
изменения мира или его таблиц.

## Брифинги

Состояние разговора хранится в `b.1m_Elder.1m_s1`, ресурс текста при этом может
оставаться прежним `briefing s1`. `ResolveBriefing("1m_s1")` возвращает явную
привязку, а `BriefingOwner` проверяет общий номер актёра и темы. Смешанные
пространства имён и неизвестный актёр отклоняются.

Завершение полной темы направляется в `1m_#OnBriefingComplete`, использует только
явно указанную запись награды и сохраняет полный GS-ключ. Оно принимается один
раз из состояния «доступно», до выдачи награды проверяется компиляция обработчика.
Для такого события не выполняются пять принудительных сегментов всего мира и
старый обработчик найма без пространства имён.

Новый выбор тем, постановка разговора на обычной карте, обработка участников
текста, полная пауза, открытие магазина по привязке `shop`, услуги и найм относятся
к следующим этапам. Существующий `I3DScreenBase` этим этапом не превращён в
интерфейс мирного поселения. Реестр предоставляет этим потребителям имена
ресурсов; наличие записи `shop` само по себе магазин не открывает.

## Сохранения и границы готовности

Этап 2 повысил схему x64 с 3 до 4; этап 3 повышает её до 5. Старые сохранения этим кандидатом не читаются;
установленный движок и существующие файлы сохранений не меняются.

Снимок содержит номер и описание модуля, таблицу локальных и внутренних ID,
источник каждого объекта, псевдонимы и контекст каждого сценарного потока.
Объекты, их AI, текущие значения переменных и очередь исполнения сохраняются
штатным графом. При восстановлении проверяется соответствие существующему
описанию и runtime identity; MOB не создаёт население повторно и не запускает
свой WorldScript заново. Удалённая сущность остаётся отсутствующей. Версия 5 также
хранит тревогу, её причины и последний сегмент происшествия, runtime identity
посетителей и предыдущие позиции для устойчивого определения границы. При
восстановлении не создаются повторные события входа. Удалённые и мёртвые
посетители не записываются. Геометрия и привязка ворот проверяются и при загрузке.
Дополнительно проверяется согласованность владельца сценария, условий,
действий и вложенных циклов.

Рендеру передаются исходный локальный NID, тип и действующий внутренний ID,
в том числе при восстановлении сохранения. Записи дополнительного MOB не
приписываются основному источнику карты. Алгоритмы рендера не меняются.

Редакция и привязки должны оставаться теми же для восстановления снимка.
Автоматической миграции сохранения при изменении описания или состава модулей
нет. При изменении содержимого MOB автор обязан увеличить `revision`.

Это фундамент этапов 2–4. Код области, тревоги и диалогов реализован; игровая
приёмка ещё не проводилась. Магазины, найм, перенос персонажей и последствия
существующих заданий остаются в этапах 5–7. Перенесённого содержимого пока нет.
В рамках текущего поручения разрешена обычная Release x64 сборка; тесты,
headless, NavBake, запуск и установка в игру не выполняются.

## Мирная область (`peace`, этап 3)

Вся логика работает в существующем `CWorldServer`. Вход и выход определяются
положением каждого живого члена отряда и подконтрольных существ; карта, партия,
HP/MP, эффекты, агрессия врагов и летящие снаряды при пересечении не сбрасываются.
Поля этой регистрации описывают геометрию и сценарий, отдельного переключателя нет.

| Поле | Смысл |
|---|---|
| `polygon` | 3–128 XY-точек выпуклого контура против часовой стрелки, внутри текущей карты. Пересекающиеся мирные области отклоняются. |
| `min_z`, `max_z` | Абсолютные пределы высоты положения ног; отдельный этаж ниже диапазона не считается Посёлком. |
| `hysteresis` | Расширение только уже существующего членства, 0–2 м; по умолчанию 0,4 м. Вход проверяется по исходному контуру. |
| `quiet_seconds` | Время без действующих причин перед снятием тревоги; по умолчанию 5 секунд игрового времени. Пауза не уменьшает его. |
| `faction` | Номер стороны жителей, без изменения дипломатии карты или масок врагов. У кандидата — 2, как у жителей исходного basecam. |
| `alarm_key` | Местный GS-ключ удержания тревоги; по умолчанию `Alarm` → `1m_Alarm`. Ненулевое значение удерживает тревогу. Ключи выходного состояния запрещены. |
| `gate.object`, `gate.exit` | ID существующих ворот основной карты и индекс её прежнего выхода. Проверяются объект, положение, прямоугольник выхода и старое назначение. |
| `gate.a`, `gate.b`, `gate.inside` | Отрезок прохода в воротах и точка на внутренней стороне. Источник события входа/выхода отмечается в журнале, проход не телепортирует персонажа. |
| `gate.legacy_zone`, `gate.legacy_entrances` | Точное старое направление и допустимые входы, превращаемые в локальный проход. Прочие направления не меняются. |

Состояния персонажа: `Outside=0`, `Peaceful=1`, `Alarm=2`, `Hostile=3`.
В мирной области штатная осторожность только от близости противника не включает
боевой интерфейс. Тревога или враждебность жителям включает боевой интерфейс
для находящихся внутри членов отряда и штатную боевую стойку. Вне области
сохраняется обычное поведение игры. Экипировка не заменяется.

Тревогу вызывают атаки и вредящие заклинания внутри области или по ней, фактический
урон, враг внутри, активная местная угроза, нативный сигнал тревоги с местным
источником и `1m_Alarm`. Нативный сброс `InvokeAlarm(0, ..., true)` не является
новым происшествием. Бой дальнего спутника снаружи сам по себе не тревожит Посёлок.
После исчезновения причин идёт затишье; выход персонажа сам по себе тревогу не снимает.

`AllowAction` используется при приёме команды, начале атаки и перед исполнением,
до расхода предмета/маны/ресурсов умения. Команды игрока, вредящие дружественной
цели из Посёлка или по Посёлку, отклоняются. Учитываются штатный классификатор
вредящих заклинаний, радиус и фильтры целей, а также радиус оружейных умений.
Дружественная установка ловушек внутри, воровство и приручение дружественных целей
в этом контуре отклоняются. Полезные заклинания и бой с настоящим врагом разрешены.
Ранее выпущенные снаряды и эффекты наносят обычный урон и могут вызвать тревогу.

`CanInteract(world, player, id, npc)` — общий предикат для следующих этапов.
Нужен живой участник внутри; при заданном NPC — живой дружественный собеседник
в той же области не дальше 4 м. Проверяются все живые члены партии и подконтрольные
существа: их текущие/следующие вредящие команды, направленная агрессия, вредящие
эффекты, входящие снаряды и заклинания. Бой спутника за пределами Посёлка закрывает
доступ к услугам, сохраняя отдельно местный режим. Интерфейсы разговора и торговли
ещё не вызывают этот предикат: их подключение относится к этапам 4–5.

Выходные GS-ключи: `1m_AlarmActive`, `1m_AlarmReasons`, `1m_Inside`, `1m_Mode`.
`Inside` — число живых посетителей партии; `Mode` — общий режим её присутствия,
а точный режим каждого персонажа возвращает `ModeFor`. Причины — битовая маска:
атака/местная угроза 1, заклинание 2, урон 4, нативная тревога 8, сценарий 16,
затишье 32. Ключи публикуются только при изменении. Входы, выходы и изменения
тревоги записываются в постоянный игровой журнал; не вызывают повторную
инициализацию MOB. Сценарные обработчики входа будут подключаться с содержимым.

Кандидат связан с текущими стенами Zone1 и воротами 1725, выходом 2 в `bz1g`.
У карты это вход 1, у трёх активных `LeaveToZone` — вход 0. Оба становятся
локальными: сервер не удаляет партию и не меняет карту, клиент не показывает
маркер/подтверждение старого перехода. Соседние команды, опыт, GS и ожидания
исходных сценариев продолжают выполняться. Полный первый разговор и дальнейшие
цепочки потребуют переноса содержимого; этот этап их не имитирует.


## Дополнение этапа 7

Актуальная схема динамических saves — v6: реестр квалифицированных целочисленных ID принадлежит кампании, ссылки сценариев на путешествующий отряд сохраняются отдельно от временного экземпляра объекта. Возврат в посещённую зону продолжает её состояние. Найм и повторный найм сохраняют публичный/map ID. Подробности и сценарии приёмки: [сохранения и найм](settlement-persistence.md). Описание v4/v5 выше фиксирует историю соответствующих этапов.
